There are six chatbots, one per platform, and they share one architecture. Each bot keeps per-channel (or per-DM) conversation history, calls the Vaquill US primary-law search API, renders citations to statutes, regulations, court rules and agency guidance, and enforces per-user rate limits.

## Shared architecture

Every chatbot receives a platform message through a webhook or WebSocket, calls `POST /api/v1/us/statutes/search`, formats the response with citations, and replies in-thread when the platform supports it. The flow matches the diagram on the [Integrations overview](/integrations#common-architecture).

<Accordion title="Shared components">
  All six bots share the same components:

  - A Vaquill client (`vaquill_client.py`) that wraps `POST /api/v1/us/statutes/search`
  - A conversation manager for per-channel or per-DM chat history
  - A rate limiter with a Redis or in-memory backend
  - Slash or prefix commands: `help`, `clear`, `examples`, `stats`
  - Citation rendering built on each platform's own primitives (Block Kit, Adaptive Cards, inline keyboards)
</Accordion>

## Pick by deployment surface

| Bot | Hosting model | Public URL required? | Documented deploy recipes |
|---|---|---|---|
| Slack | Socket Mode (no URL) or HTTP | HTTP mode only | Docker Compose, Docker, Railway, Render, Fly.io, VPS + nginx |
| Discord | Outbound WebSocket (Discord gateway) | No | Docker, Railway, Render, VPS + systemd, Fly.io |
| Microsoft Teams | HTTP via Azure Bot Framework | Yes | Docker, Azure Web App, Railway, Render |
| Telegram | Polling or webhook | Webhook mode only | Docker, Render, Railway, VPS + systemd, Fly.io |
| WhatsApp | HTTP via Twilio webhooks | Yes | Docker, Render, Railway, Fly.io, VPS |
| Signal | HTTP via signal-cli-rest-api | No (internal Docker network) | Docker Compose, Dokploy |

To avoid exposing any ports during development, use Slack (Socket Mode), Discord, Telegram (polling), or Signal. None of them need a public URL.

<Accordion title="Deploy targets">
  All six bots ship with Dockerfiles and have been smoke-tested on these targets:

  - Docker Compose (recommended for self-hosting)
  - Railway (Git-based deploys)
  - Render (free tier with cold starts)
  - Fly.io (low-latency regions)
  - VPS + systemd (full control)
  - Azure App Service (Teams bot only)

  Each bot's page has its own deployment recipe.
</Accordion>

## Shared bot settings

Every bot reads these variables, plus its own platform-specific ones on its page.

| Variable | Required | Default | Description |
|---|---|---|---|
| `VAQUILL_API_KEY` | Yes | - | Vaquill API key (`vq_key_...`) |
| `VAQUILL_API_URL` | No | `https://api.vaquill.ai/api/v1` | API base URL |
| `VAQUILL_MODE` | No | `standard` | Default search mode: `standard` (faster) or `deep` (more thorough). WhatsApp users switch it with `/mode`. |
| `VAQUILL_COUNTRY_CODE` | No | - | Jurisdiction filter, e.g. `US` |
| `REDIS_URL` | No | - | Optional Redis URL. Enables distributed rate limiting (Slack, Discord, Teams) and persistent sessions and rate limits (WhatsApp). |

Rate-limit variables differ per bot and are listed on each page.
For `401`, `402` and `429` responses from the API, see the [Errors reference](/api-guide/errors).
