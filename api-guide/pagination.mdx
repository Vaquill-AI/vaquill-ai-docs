Nine endpoints take a `limit`, and they page in two different models.

**Offset paging** walks a fixed window with `limit` and `offset` and stops when `hasMore` is `false`.
Use it for a ranked or ordered list that is not changing while you read it.

**Cursor paging** walks an append-only log by change `id`, forwards with `sinceId` or backwards with `beforeId`.
Use it for change history, where new rows land while you page and an offset would skip or repeat them.

| Endpoint | Model | Notes | `limit` default | `limit` max |
|---|---|---|---:|---:|
| `POST /us/statutes/search` | offset | See [Search paging](#search-paging) | 10 | 50 |
| `GET /boards` | offset | Returns `data.total` and `data.hasMore` | 500 | 500 |
| `GET /watches` | offset | Returns no total and no `hasMore` | 100 | 200 |
| `GET /watches/{id}/changes` | cursor, in `meta.cursor` | `sinceId` and `beforeId` | 50 | 200 |
| `GET /watches/{id}/deliveries` | cursor backwards, `beforeId` from `meta.nextBeforeId` | Newest first | 50 | 200 |
| `GET /us/statutes/section/{actId}/changes` | cursor, top-level `cursor` | `sinceId` and `beforeId` | 50 | 200 |
| `GET /us/statutes/section/{actId}/cited-by` | offset, resume with `nextOffset` | `offset` 0 to 5,000. A page past the end is empty and not charged | 25 | 100 |
| `GET /us/statutes/section/{actId}/cross-state` | `limit` only | Top N by relevance, no page two | 5 | 25 |
| `GET /us/statutes/section/{actId}/related` | `limit` only | Top N by relevance, no page two | 3 | 10 |

`cross-state` and `related` have no page two, so raise `limit` to its maximum if you want the whole set.

<Accordion title="How cited-by pages">
  `cited-by` pages on `offset`. Pass the previous response's `nextOffset` as `offset` while `hasMore` is true.
  `total` is the count of citing sections across all pages (a lower bound when `totalCitersIsLowerBound` is true). `returned` is the number of rows on this page.
</Accordion>

## Search paging

`POST /us/statutes/search` is the endpoint most integrations page. Two request fields set the window, and one response flag tells you when to stop.

| Field | Type | Default | Range | Purpose |
|-------|------|---------|-------|---------|
| `limit` | int | 10 | 1 to 50 | Page size, the number of results returned |
| `offset` | int | 0 | 0 to 70 (0 to 10,000 with `matchType: "boolean"`) | Number of results to skip before this page |

### Response fields

Each search response includes these top-level fields:

- `results`: the array of result objects for this page.
- `count`: the number of results returned on this page, not the corpus-wide match count.
- `total`: a deprecated alias for `count`. Read `count` in new code. It is never a corpus total.
- `offset`: the offset that was applied.
- `hasMore`: `true` when more results are reachable beyond this page.
- `changedSectionCount`: only when `changedSince` is set. How many sections changed in that window, before ranking.
- `creditsConsumed`: what this call cost.

<Warning>
  `count` and `hasMore` describe the results this query can reach, not the corpus. No field reports the total number of matches.
  Loop on `hasMore`, and narrow the query instead of paging deeper.
</Warning>

### How deep you can page

The deepest reachable result is `offset + limit`.
Ranked modes (`any`, `all`, `phrase`) rank a pool of 120 results once per query, so every page is a free slice of that ranking.
`hasMore` is `false` on the last reachable page. With the largest page size, `offset` 70 reaches the end of the pool:

```json
{ "query": "data breach notification", "limit": 50, "offset": 70 }
```

`matchType: "boolean"` pages to the end of the matches.
Keep `limit` at 50 or below and send each `nextOffset` back as `offset` until `hasMore` is `false`.
To survey a jurisdiction more broadly, scope with `corpusType` and `state` and run several narrower queries, as [Best practices](/api-guide/best-practices) describes.

### Page until hasMore is false

This loop walks every reachable page of a ranked search.

<Warning>
  The last ranked page is clamped to `offset` 70, so with `page_size` 50 it overlaps the page before it. The loop drops repeats by `actId`.
</Warning>

<CodeGroup>
```python Python
import requests

def search_all(query, corpus_type=None, state=None, page_size=50):
    url = "https://api.vaquill.ai/api/v1/us/statutes/search"
    headers = {
        "Authorization": "Bearer vq_key_...",
        "Content-Type": "application/json",
    }
    results, seen = [], set()
    offset = 0
    while True:
        body = {"query": query, "limit": page_size, "offset": offset}
        if corpus_type:
            body["corpusType"] = corpus_type
        if state:
            body["state"] = state

        data = requests.post(url, headers=headers, json=body).json()
        for row in data["results"]:
            # The clamped last page overlaps the one before it.
            if row["actId"] not in seen:
                seen.add(row["actId"])
                results.append(row)

        # Stop when the API says there is no more, or we hit the offset cap.
        if not data["hasMore"] or offset >= 70:
            break
        offset = min(offset + page_size, 70)

    return results

sections = search_all("data breach notification", corpus_type="STATE", state="ca")
print(len(sections))
```

```javascript JavaScript
async function searchAll(query, { corpusType, state, pageSize = 50 } = {}) {
  const url = "https://api.vaquill.ai/api/v1/us/statutes/search";
  const headers = {
    Authorization: "Bearer vq_key_...",
    "Content-Type": "application/json",
  };
  const results = [];
  const seen = new Set();
  let offset = 0;

  while (true) {
    const body = { query, limit: pageSize, offset };
    if (corpusType) body.corpusType = corpusType;
    if (state) body.state = state;

    const data = await (
      await fetch(url, { method: "POST", headers, body: JSON.stringify(body) })
    ).json();
    for (const row of data.results) {
      // The clamped last page overlaps the one before it.
      if (!seen.has(row.actId)) {
        seen.add(row.actId);
        results.push(row);
      }
    }

    if (!data.hasMore || offset >= 70) break;
    offset = Math.min(offset + pageSize, 70);
  }
  return results;
}

const sections = await searchAll("data breach notification", {
  corpusType: "STATE",
  state: "ca",
});
console.log(sections.length);
```

## Offset paging on the list endpoints

`GET /boards` and `GET /watches` both take `limit` and `offset` and return their page inside `data`.

`GET /boards` returns `data.total` and `data.hasMore`.
`GET /watches` returns neither. Advance `offset` until a page comes back shorter than `limit`. One page is enough there, because the watch cap (see [Law change alerts](/api-guide/alerts)) never exceeds the default `limit` of 100.

The `GET /boards` `limit` defaults to 500, which is also the maximum.
Page on `offset` using `hasMore` instead of trusting one call.

```python Python
import requests

def all_boards():
    url = "https://api.vaquill.ai/api/v1/boards"
    headers = {"Authorization": "Bearer vq_key_..."}
    boards, offset = [], 0
    while True:
        data = requests.get(
            url, headers=headers, params={"limit": 500, "offset": offset}
        ).json()["data"]
        boards.extend(data["boards"])
        # Stop on the API's own flag, not on len(boards) == total.
        if not data.get("hasMore"):
            break
        offset += 500
    return boards

print(len(all_boards()))
```

## Cursor paging on change history

`GET /watches/{id}/changes` and `GET /us/statutes/section/{actId}/changes` page by change `id`, not by offset.
`GET /watches/{id}/deliveries` uses the same backwards `beforeId` contract, with the next cursor in `meta.nextBeforeId`.
Change ids only increase, so an id is a stable position in the log.

| Parameter | Direction | Purpose |
|---|---|---|
| `sinceId` | forwards | Return changes with an `id` **greater** than this. The polling cursor. |
| `beforeId` | backwards | Return changes with an `id` **less** than this. How you walk into history. |
| `order` | either | `desc` (default) newest first, `asc` when catching up from a cursor. |
| `limit` | either | 1 to 200, default 50. |
| `changeKind` | filter | `added`, `amended` or `removed`. Repeatable. |

The two endpoints return the cursor in different places:

- `GET /watches/{id}/changes` returns it as `meta.cursor`, alongside `meta.hasMore`.
- `GET /us/statutes/section/{actId}/changes` returns it as a top-level `cursor`, alongside a top-level `hasMore`.

The cursor is the highest `id` on the page. It is `null` on an empty page, so an idle poll must keep the cursor it already holds.

To poll forwards, save the cursor and pass it as `sinceId` with `order=asc` on the next call.

To walk backwards, pass the lowest `id` you have seen as `beforeId`, with the default `order=desc`.
Repeat until a page comes back short of `limit`.

```python Python
import requests

def backfill(act_id, headers):
    """Walk a section's change history backwards, oldest page last."""
    url = f"https://api.vaquill.ai/api/v1/us/statutes/section/{act_id}/changes"
    before, out = None, []
    while True:
        params = {"limit": 200, "order": "desc"}
        if before is not None:
            params["beforeId"] = before
        page = requests.get(url, headers=headers, params=params).json()
        changes = page["changes"]
        out.extend(changes)
        if not page["hasMore"] or not changes:
            break
        # Lowest id on this page is where the next page starts.
        before = min(c["id"] for c in changes)
    return out
```

<Warning>
  On both change endpoints, `hasMore` means this page filled to `limit`. The next page can be empty. Treat an empty page as the end.
</Warning>
