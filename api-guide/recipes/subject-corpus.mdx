Build a complete set of the sections on one subject, and get notified when any of them change.

Ranked search returns the most relevant matches, not all of them. This recipe lists the corpus by enumeration and uses search only to narrow it.

<Steps>

<Step title="Size the job">

Check how big the job is before you walk anything.

```bash
curl -X POST "https://api.vaquill.ai/api/v1/us/statutes/count" \
  -H "Authorization: Bearer $VAQUILL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"state": "tx", "corpusType": "REGULATION"}'

# { "count": 43638, "isExact": true, ... }
```

`POST /us/statutes/count` takes the search filters but no `query`. It returns an exact section count for one credit.
A scope that matches nothing is refunded.

</Step>

<Step title="Enumerate the spine">

Walk `GET /us/statutes/divisions` for each jurisdiction and each corpus you care about.
It lists one level at a time. The leaf level returns every section in a container with its `actId`.

```bash
# 1. the codes a jurisdiction publishes
curl -H "Authorization: Bearer $VAQUILL_API_KEY" \
  "https://api.vaquill.ai/api/v1/us/statutes/divisions?state=tx&corpusType=REGULATION"

# 2. the chapters in one code
curl -H "Authorization: Bearer $VAQUILL_API_KEY" \
  "https://api.vaquill.ai/api/v1/us/statutes/divisions?state=tx&corpusType=REGULATION&code=tx_26"

# 3. every section in one chapter, each with an actId
curl -H "Authorization: Bearer $VAQUILL_API_KEY" \
  "https://api.vaquill.ai/api/v1/us/statutes/divisions?state=tx&corpusType=REGULATION&code=tx_26&chapter=554"
```

Store the `actId`, citation, title and hierarchy path for every leaf.

<Accordion title="Enumeration tips">
  - **Depth varies.** Some codes publish sections directly under the code. Read `level` on each response. Treat any node with `isLeaf` and an `actId` as a section.
  - **Skip repealed law.** Pass `excludeRepealed=true` (or `actStatus=` for the inverse) to list only operative law.
  - **Check the count.** Interior nodes carry a `sectionCount`. Compare it with the leaves you received and log any mismatch.
</Accordion>

</Step>

<Step title="Narrow to your subject">

Run one scoped query per concept, filtered to one jurisdiction and one corpus type, at the largest page size.

```json
{
  "query": "automated external defibrillator",
  "state": "tx",
  "corpusType": "REGULATION",
  "limit": 50,
  "offset": 0
}
```

Page to the end of the results, then repeat for the next concept and union the `actId` values.
Intersect that union with the spine from step 2.

Use one query per concept. Search has no query operators, so `defibrillator OR cardiac arrest` is read as one string.
See [How search works](/api-guide/concepts/search).

</Step>

<Step title="Hydrate what survives">

Fetch in batches of 50 with `POST /us/statutes/sections`.
Add `includeBody` to get the text in the same call.

```json
{ "actIds": ["STATE_TX_TAC_T26_P1_C554_S554_1935", "..."], "includeBody": true }
```

Full text costs more. Fetch metadata for the whole candidate set first, then run a second pass with `includeBody` for the sections you keep.
Rows with `body: null` are not charged. Read `creditsConsumed` on each response.

</Step>

<Step title="Subscribe, then re-hydrate">

Create a board watch for each `(corpusType, state)` pair in scope. Poll `GET /api/v1/watches/{id}/changes` with `sinceId` paging on your own schedule.
Re-fetch only the `actId` values that appear.

```bash
curl -X POST "https://api.vaquill.ai/api/v1/watches" \
  -H "Authorization: Bearer $VAQUILL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"corpusType": "REGULATION", "state": "tx", "channel": "webhook", "webhookUrl": "https://example.com/hooks/vaquill"}'
```

[Law change alerts](/api-guide/alerts) lists the boards you can watch and the channel options.

A watch returns the source's full captured history, not only changes after you subscribe. Watch management and polling cost no credits.

Use `changedSince` on search to see what moved among the sections you already track.

</Step>

</Steps>

## Keeping the spine honest

Re-run the enumeration in step 2 less often than your change polling, such as quarterly.
It catches structural change: a chapter that gained sections, or a code that was reorganized.

Compare the new enumeration with the stored one:

| Case | Meaning |
|---|---|
| In the new spine, not the old | Newly published, or newly in scope |
| In both | Compare `lastAmendedYear` to decide whether to re-hydrate |
| In the old spine, not the new | Repealed, renumbered, or recodified. An `actId` changes when a section is renumbered, so re-resolve by citation through `GET /us/statutes/resolve` before you retire a record |
