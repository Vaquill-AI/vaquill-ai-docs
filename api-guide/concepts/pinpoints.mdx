title: "Pinpoints"
description: "Get the text of one subsection, paragraph or clause instead of the whole section, and learn how far to trust it."
---

A pinpoint citation such as `625 ILCS 5/11-601(c)` names one subsection of a section.
The API returns that unit with its own text, the text it completes, and where it sits in the section.

```bash
curl "https://api.vaquill.ai/api/v1/us/statutes/resolve?cite=625%20ILCS%205/11-601(c)&state=il" \
  -H "Authorization: Bearer vq_key_..."
```

The response carries the whole section as before, and a `pinpoint` object beside it.

| Field | Meaning |
|---|---|
| `requested`, `path`, `label`, `level` | The pinpoint as sent, its path (outermost label first), the unit's own label and its level |
| `matched`, `matchLevel` | Whether the unit exists. See [Always read `matched`](#always-read-matched) |
| `text`, `leadIn`, `fullText` | The unit's own text, the text it completes, and the unit as printed with its sub-units |
| `children`, `siblings` | The sub-units, and the labels of the previous and next unit at the same level |
| `charStart`, `charEnd` | The unit's character offsets in the section `plain` text |
| `structure` | Where the outline came from. See [How far to trust it](#how-far-to-trust-it-structure) |

## Where it works

| Route | How to ask | What you get |
|---|---|---|
| `GET /us/statutes/resolve`, `POST /us/statutes/resolve` | Put the pinpoint in the citation | `pinpoint` on the response, and on each item of a batch |
| `POST /us/statutes/extract-citations` | Send `resolve: true` | `pinpointMatch` on each resolved row with a pinpoint, plus `charStart` / `charEnd` for its span in your text. A range returns its two ends (`rangeRole`, `rangePartner`) |
| `GET /us/statutes/section/{actId}/body` | `pinpoint=(c)(1)` | `pinpoint` beside the full body |
| `POST /us/statutes/search` | `includePinpoint: true` | `pinpoints`, keyed by `actId` |

Pinpoints add no cost. See the [Errors table](#errors) for misses.

## What a pinpoint can look like

The pinpoint is read from the end of the citation.
Labels are in parentheses, outermost first. A label with a hyphen or a dot is one label.

| You send | Path |
|---|---|
| `625 ILCS 5/11-601(c)(1)` | `["c", "1"]` |
| `625 ILCS 5/11-601(d-1)` | `["d-1"]` |
| `625 ILCS 5/11-601(f)(1.5)` | `["f", "1.5"]` |
| `Minn. Stat. § 245D.10, subd. 2(1)` | `["2", "1"]` |
| `Iowa Code § 88.9(1)(a)` | `["1", "a"]` |
| `Mo. Rev. Stat. § 556.061(2)(a)` | `["2", "a"]` |
| `Wis. Stat. § 48.02(1)(a)` | `["1", "a"]` |

`(f)(1.5)` is the unit `1.5` inside `(f)`.

Ranges and lists (`(a)-(c)`, `(a), (b)`) resolve to the first unit.
`kind` says so, and `also` lists the others.
Fetch each one with `GET /us/statutes/section/{actId}/body?pinpoint=...`.

State forms are read too, such as Minnesota `subd.`, Kentucky `Section 8(2)(a)`, Wisconsin inserts like `(am)` and `(1m)`, and Spanish forms for Puerto Rico.

The `subsection` string on the section is dot-joined (`f.1.5`). Read `pinpoint.path` for the exact unit.

## Always read `matched`

A pinpoint can name a unit the section does not have.
The call still succeeds because the section resolved.

| `matchLevel` | Meaning | What the block describes |
|---|---|---|
| `exact` | The whole path exists | The unit you asked for |
| `ancestor` | Only a leading part of the path exists | The deepest unit that does. `unmatched` lists the part that did not exist, for example `["7"]` when you asked for `(c)(7)` and the section ends at `(c)(4)` |
| `none` | Not even the first label exists, or the outline could not be recovered | Nothing. Read `reason` |

On a miss, `available` lists the labels that exist at the level where the lookup stopped.
`reason` is `no_such_subsection` or `no_structure`. With `no_structure` the section text is still at `/body`.

If the pinpoint could not be looked up at all, the response has `pinpointNote` instead of `pinpoint`. Retrying usually works.

## How far to trust it: `structure`

Every pinpoint says where its outline came from.

| `structure.quality` | Meaning |
|---|---|
| `native` | Built from the publisher's own markup |
| `verified` | Parsed from the text and passed every check |
| `heuristic` | Parsed from the text and failed a check. Confirm against the text |
| `none` | No outline could be recovered |

`structure.source` is `artifact` for a pre-built outline and `request_time` for one parsed on this request.
`structure.textSha256` is the SHA-256 of the `plain` text that `charStart` and `charEnd` index into.
Hash your copy of `plain` to confirm the offsets apply to it.

If a unit's `text` is empty and `children` is not, read the children.

## Search: which subsection matched

With `includePinpoint: true`, each search hit also says which subsection it matched, in a `pinpoints` object keyed by `actId`.

```json
{ "query": "30 mph urban district speed limit", "state": "il", "includePinpoint": true }
```

Each hit has `located`, `pinpoint` (`(c)(1)`), a `citation` you can pass to `resolve`, the unit's `text`, its `leadIn` and character offsets.
`matchedBy` is `passage` or `query`.
When several sub-units matched equally well, `scope` is `parent` and the block names their common parent.

A hit that cannot be named says why in `reason` (`no_single_unit`, `no_structure`). Results and price are unchanged.

## Errors

| Status | When | Charged |
|---|---|---|
| `422` | A malformed `pinpoint` on `/body`, or `pinpoint` sent together with `asOf` | No |
| `200` | A pinpoint that names a unit the section does not have (`matched: false`) | Yes, like any resolved section |
| `200` | A pinpoint we could not look up (`pinpointNote`) | Yes. The section resolved |
